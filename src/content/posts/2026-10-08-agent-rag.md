1. 离线存储：首先对原始文档进行解析、清洗和切分。常见切分方式包括固定 Token 切分、段落切分、递归切分、语义切分和父子切分。通用场景可以从 500 tokens + 50 tokens overlap 开始测试；父子切分采用“小块检索、大块提供给 LLM”的方式，兼顾检索精度与上下文完整性。每个 Chunk 逻辑上包含向量、原文和 Metadata：向量用于检索，原文用于提供给 LLM，Metadata 用于权限过滤、版本管理和来源溯源。最后使用 Embedding 模型将 Chunk 转换为向量，存入 Chroma（更适合本地启动）、Milvus（大数据向量查询）、Qdrant（线上方案中庸）、Weaviate 等向量数据库。

2. 在线检索：首先结合对话上下文对用户 Query 进行补全、改写或拆分，使其更适合检索；然后通过向量检索、BM25 等方式召回候选 Chunk。粗排阶段强调召回率，一般获取 Top 50～200 个候选；精排阶段使用 Cross-Encoder 或 Reranker 重新计算 Query 与候选内容的相关性，最终保留 Top 3～10。之后进行去重、相邻 Chunk 合并、父块回查和 Token 预算控制，再将证据拼接进 Prompt 交给 LLM。temperature 控制生成随机性，不决定 Prompt 如何拼接；知识问答通常设置为 0～0.3。

3. Embedding 模型选型：需要重点关注模型是否适合中文或多语言、向量维度、最大输入长度、检索效果、推理速度和部署成本。中文场景可以评估 BGE、GTE、E5 等模型。还要确认模型是否要求为 Query 和 Document 添加不同前缀，以及向量是否需要归一化。向量维度越高不一定效果越好，还会增加存储空间和检索成本。模型最终应通过业务评测集选择，而不是只参考公开排行榜。

4. 向量数据库：向量数据库是专门为高维向量存储和近似最近邻搜索设计的数据库。它可以根据 Query 向量，从大量文档向量中快速找到最相似的 Top-K 结果，并支持余弦相似度、点积、欧氏距离等计算方式。常见向量数据库包括 Chroma、Milvus、Qdrant 和 Weaviate。生产选型还需要关注 Metadata 过滤、索引类型、数据规模、并发能力、分片副本、多租户和运维成本。

5. 精排：Cross-Encoder 会将 Query 和候选 Chunk 一起输入模型，通过充分的 Token 级交互判断两者的相关程度。相比用于粗排的 Bi-Encoder，Cross-Encoder 通常更加准确，但计算成本和延迟也更高。因此，常见做法是先通过向量检索或 BM25 召回几十到几百个候选，再使用 Cross-Encoder 精排，最终选出少量高质量证据。

 6. 粗排与多路召回：单一检索方式很难覆盖所有问题，因此生产系统通常采用多路召回。向量检索适合语义相似但表达不同的问题，BM25 适合错误码、型号、条款编号、专有名词等精确匹配场景，还可以增加标题召回、FAQ 召回、图谱召回和结构化数据查询。不同通道的分数不能直接相加，通常使用分数归一化、加权融合或 RRF 进行结果融合，然后再去重和精排。

 7. 标准在线链路： Query 改写或拆分 → 权限、地区、产品、时间等 Metadata 硬过滤 → 向量检索、BM25、图谱等多路召回 → 候选融合与去重 → Cross-Encoder 精排 → 父块回查与上下文扩展 → Prompt 拼装 → LLM 生成 → 引用校验与安全检查

8. 图数据库增强检索：图数据库适合处理实体关系和多跳查询。例如回答“今日头条 CEO 所在公司的竞争对手有哪些”时，可以先识别人物、公司和竞争关系，再沿图谱查询实体路径。Graph RAG 中通常由图数据库定位实体和关系，由向量数据库召回相关原始文档，最后由原文提供回答证据。图数据库不应完全替代原始文档，因为图谱可能无法完整表达条件、例外和上下文。

9. RAG 评估：RAG 评估可以分为检索层、生成层和端到端业务层。检索层关注正确证据是否被召回以及排序是否合理，常见指标包括 Recall@K、Precision@K、MRR、NDCG 和 Hit Rate；生成层关注答案正确性、完整性、忠实度、幻觉率、引用准确率和拒答准确率；业务层关注问题解决率、人工转接率、用户满意度、响应延迟和单次请求成本。

10. RAG 知识库更新：RAG 可以增量更新，但需要考虑文档变化引起的 Chunk 边界变化。常见做法是通过定时任务、消息队列、Webhook 或 CDC 监听文档变更，先计算文档Hash，再对变化文档重新解析和切分，并通过 Chunk Hash 复用未变化的向量。生产环境建议采用版本化发布：先构建新索引并执行离线评测，再进行小流量灰度；确认效果和线上返回没有明显异常后，切换正式版本，最后延迟删除旧数据。旧版本应保留一段时间，以便快速回滚。

11. RAG 的主要难点：

* 文档预处理：需要解决 PDF 版面恢复、OCR 错误、表格解析、标题层级丢失、重复内容、Chunk 边界和 Metadata 缺失等问题。
* 检索质量调优：需要平衡 Chunk 大小、Overlap、Top-K、向量检索与关键词检索、精排模型、结果去重、时效性和权威度。
* 效果评估：需要构建高质量评测集，并区分问题来自检索阶段还是生成阶段。
* 成本与延迟：Query 改写、多路召回、精排、长上下文和 LLM 生成都会增加延迟与成本，需要在效果、延迟和成本之间进行平衡。
* OCR 与多模态模型原理：传统 OCR 主要通过文字区域检测、方向校正、文字识别和版面分析，将图片中的文字及其位置提取出来。多模态模型通常使用视觉编码器或音频编码器，将图片、音频转换为视觉或音频特征，再通过 Projector 或 Adapter 映射到 LLM 能够处理的表示空间，与文本 Token 一起参与推理。因此，“把图片或音频翻译成词交给 LLM”可以作为直观理解，但严格来说，它们通常被转换为视觉 Token、音频 Token 或连续特征，并不是简单地加入文本词表。
* 知识冲突处理：当检索到的知识相互冲突时，不能简单选择向量相似度最高的文档，因为相似度只能表示语义相关性，不能表示文档是否权威、最新或适用。应先根
* 据租户权限、用户身份、地区、产品和时间等条件过滤，再根据文档状态、生效区间、版本和来源权威度进行裁决，最后才使用相关性分数排序。入库时应保存来源、负责人、权威等级、版本、状态、生效时间、失效时间和适用范围；离线和在线阶段都应检测冲突；生成答案时逐条引用证据。对于无法自动裁决的冲突，应明确展示不同说法或转人工审核，而不是让 LLM 自行猜测。
