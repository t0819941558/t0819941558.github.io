\## 二、学习日志（query + 结论 + 方法论）



\### 2026-08-22



\#### ①【理解】从 scripts 入手建立全局认知

\- \*\*query\*\*："先给我将packagejson下的scripts 每行命令注释给我加一下，都做了啥。我希望从入口去找寻学习"

\- \*\*思路\*\*：不看代码先看 \`package.json\` 的 scripts——37 条命令就是"这个仓库能干什么"的地图。

\- \*\*关键发现\*\*：\`build\` 命令里的 cd 顺序（tui→telemetry→ai→agent→…→coding-agent）就是包编译依赖顺序的可执行版本；质量门禁是 \`check\`（biome+类型+锁校验）+ \`test\`。



\#### ②【行动】pi-test.sh 的澄清

\- \*\*query\*\*："帮我给pi-test.sh 文件加注释，你为什么知道这个文件是入口？"（随后："你直接在原有代码上写就行"）

\- \*\*结论\*\*：它不是程序入口，是\*\*开发启动器\*\*。真正入口是最后一行调用的 \`packages/coding-agent/src/cli.ts\`。

\- \*\*设计点\*\*：tsx 免编译直跑源码；\`--no-env\` 的 30 行 unset 清单 = pi 支持的全部 provider 列表；\`SCRIPT_DIR\` 定位支持任意目录调用。

\- \*\*行动\*\*：已在 pi-test.sh 原文件写好中文注释。



\#### ③【理解】工具链概念补盲

\- \*\*query\*\*："vitest是啥？tsgo 是啥？" / "biome给我介绍下" / "ts-node是什么来着？执行js文件吗"

\- \*\*结论\*\*：vitest=测试框架（evals 用它做行为评测底座）；tsgo=Go 重写的 TS 编译器；biome=Rust 写的 ESLint+Prettier 二合一；ts-node 老一代（慢）→ tsx 新一代（esbuild）→ node 24 原生 type-stripping 是未来。

\- \*\*认知收获\*\*：pi 工具链选型共同逻辑——全部为速度重写，这是"每提交必检查"文化的技术前提。



\#### ③+【理解】pi 技术选型的整体收益：为什么开发体验快（2026-08-24 补）



\- \*\*背景\*\*：跑 dsh 的 \`pnpm run build\`（45 包+web 前端全量编译）等到抓狂，回头才发现 pi 文档从没系统回答过"pi 为什么快"——选型散落在各处，此处统一归档。

\- \*\*pi 的三层速度设计\*\*：



\| 层 | pi 的选择 | 收益 |

\|---|---|---|

\| \*\*开发回路\*\* | \`pi-test.sh\` 用 \*\*tsx 直跑 TS 源码\*\*，免编译 | 改完代码立即跑，0 编译等待——pi 学习全程没 build 过一次 |

\| \*\*编译检查\*\* | \*\*tsgo\*\*（Go 重写的 tsc）做类型检查 | 比官方 tsc 快 10 倍级；dsh 还在用 \`tsc -b\` 全量项目引用编译 |

\| \*\*lint/格式化\*\* | \*\*biome\*\*（Rust 写的 ESLint+Prettier 二合一） | 单次全仓扫描毫秒-秒级；dsh 用 oxlint（同思路） |



\- \*\*对照 dsh 的结构性差异\*\*：pi 10 包单层 workspace + tsx 免编译回路；dsh 45 包两层嵌套 + \`tsc -b\` 项目引用全量编译 + web 前端构建。\*\*dsh 慢不是实现差，是形态不同\*\*——dsh 在向"可分发产品"走（build 一次产物用很久 + snapshot 回放测试），pi 是开发者自用工具（改完立刻跑）。

\- \*\*选型背后的共同逻辑\*\*：pi 作者把"每提交必检查"当文化——检查必须快到开发者不抵触，所以工具链全部为速度重写（tsx/tsgo/biome 分别用 esbuild/Go/Rust 碾压 JS 实现的前辈）。\*\*工具链速度决定工程文化能不能成立\*\*。

\- \*\*给自己的借鉴\*\*：做项目时先想清楚形态——"自用工具"照 pi 抄（tsx 免编译回路优先）；要分发的产品才需要 dsh 那种重构建管线，但也要给开发者留 tsx 类的快速回路，否则贡献者会被 build 时间劝退。



\#### ③++【理解】tsx 是什么、依赖谁（2026-08-24 补）



\- \*\*query\*\*："tsx是啥来着" / "tsx用的依赖是哪个？"

\- \*\*tsx = TypeScript 直接执行器\*\*：不用先编译成 JS，\`tsx cli.ts\` 拿来就跑。pi-test.sh 最后一行的发动机——改注释、插探针立即生效全靠它。

\- \*\*快的原理："转译不检查"\*\*：底层 esbuild 把 TS 类型注解直接抹掉（type stripping）变成 JS，不做类型检查——运行和检查解耦：跑的时候不查（tsx），查的时候不跑（tsgo 单独做）。

\- \*\*依赖结构（极简）\*\*：运行时硬依赖只有 \*\*esbuild ~0.28\*\*（Go 写的转译引擎，速度全部来源；Go 编译成原生二进制，按平台分发 @esbuild/darwin-arm64 等）；可选依赖 fsevents（macOS 文件监听，watch 模式用）。tsx 自己是 JS 薄壳：挂 node 模块加载钩子、解析 tsconfig paths 别名、ESM/CJS 互操作。

\- \*\*一句话记忆\*\*：\*\*tsx = esbuild（转译引擎）+ node 加载钩子（薄壳）\*\*——技术含量在 esbuild，tsx 是优秀的"接线员"。

\- \*\*族谱定位\*\*：ts-node（老一代 JS 实现，慢）→ tsx（esbuild/Go，快 10-100 倍）→ node 24 原生 type-stripping（未来不需要工具；v24 已内置但 tsx 还管 paths 别名/monorepo 解析等复杂场景）。



\#### ④【理解】tsconfig paths 的两套映射（含一次纠错）

\- \*\*query\*\*："compilerOptions下的paths引用了其他目录的 dist，的作用是什么？打包到一起吗？"（随后纠正我："我说的是这个路径，你再判断下 …/tsconfig.build.json"）

\- \*\*结论\*\*：paths 不是打包，是编译器的"改名换址"。根 tsconfig → 兄弟包 src（开发用）；tsconfig.build.json → 兄弟包 dist/*.d.ts（构建用，配合依赖序编译）。

\- \*\*方法论\*\*：给 AI 具体文件路径比描述概念更可靠。

\- \*\*定位\*\*：agent.ts 160-164 行（类型定义）+ runWithLifecycle 504-531 行。

\- \*\*结论\*\*：activeRun 不是阻止打断，恰恰是\*\*实现安全打断的载体\*\*，一鱼三吃：

  1. \*\*互斥锁\*\*：prompt() 开头 \`if (this.activeRun) throw\`，防两个 loop 并发读写 messages 搞乱历史——拦的是"再起炉灶"，不是拦"打断"；

  2. \*\*abort 的靶子\*\*：abort() 拿 \`activeRun.abortController\`，signal 一路传进 LLM 的 HTTP 流和工具执行，没有它 abort 不知掐谁；

  3. \*\*等待句柄\*\*：waitUntilIdle() 返回 \`activeRun.promise\`，finishRun 里 resolve() 唤醒等待者。

\- \*\*细节\*\*：abort 后 loop 以 aborted 错误抛出，handleRunFailure 检查 \`signal.aborted\` 把 stopReason 标成 \`"aborted"\` 而非 \`"error"\`，包装成正常 assistant 消息发事件——\*\*打断不是崩溃，是体面的、状态一致的收尾\*\*，然后 finishRun 复位 isStreaming、清空 activeRun。

\- \*\*方法论\*\*：\`try { await executor } catch { handleRunFailure } finally { finishRun() }\` 的生命周期三段式，是"可中断任务"的标准写法。

\### ㉑【理解】Tool 的本质



\- \*\*query1\*\*："我觉得你先给我讲清楚 tool是干啥用的？为什么会有这个东西，以及如何调用的"

\- \*\*Tool 的本质（讲透版）\*\*：LLM 只会生成文本，不能动手。Tool = 一份契约分两半——给模型的"说明书"（name+description+参数schema，随请求发给 LLM）+ 给程序的"执行体"（execute 函数，真正跑 fs/bash）。模型"调用工具"只是\*\*输出一段结构化 JSON 文本\*\*，harness 解析后真正执行，结果包装成 toolResult 消息回喂进对话历史，模型下一轮基于事实继续。智能（决策）与能力（执行）解耦，工具层 = agent 世界的系统调用层。

\- \*\*调用闭环五步\*\*：①请求带工具清单 → ②模型输出 tool_call JSON → ③harness prepareArguments 纠偏+execute 真执行 → ④toolResult 回喂历史 → ⑤模型不再调工具则循环结束（runLoop 内层 while）。

\- \*\*实验实证（探针日志骨架）\*\*：一句"读 package.json"的真实流量 = 请求①（带4工具说明书）→ thinking_delta ×19 → toolcall_delta 逐字流出 JSON → done → 执行 read → 结果回喂 → 请求②（历史变 user→assistant→toolResult）→ text_delta 输出答案。读过的代码在真实流量里全部指认现场。

  1. \`withFileMutationQueue\` 同文件编辑串行化，防并发写穿；

\- \*\*execute 流程图\*\*：模型输出(可能不规矩) → prepareArguments 纠偏 → validateEditInput → withFileMutationQueue 拿锁 → 读文件 → 归一化 → applyEditsToNormalizedContent（匹配算法在 edit-diff.ts，暂未精读）→ 还原行尾 → 写回 → 生成 diff 给人看 + 成功文本给模型。

\### ㉔【理解】compaction 上下文压缩



\- \*\*核心问题\*\*：上下文快爆时怎么丢历史不丢记忆。

\- \*\*①什么时候压\*\*：shouldCompact 一行逻辑 \`contextTokens > contextWindow - reserveTokens\`（状态栏百分比的来源）；estimateContextTokens 的巧劲——最后一条 assistant 消息的 usage 是 API 返回的真实数，只估算其后的新消息，不全量重算。

\- \*\*②在哪切\*\*：findCutPoint 从最新往最旧累加 token，攒够 keepRecentTokens 预算找最近"合法切点"（turn 边界——不能把 toolCall 和它的 toolResult 切两半）。\*\*isSplitTurn 精妙概念\*\*：切点落在 turn 中间说明"最近这轮工作"本身超大，pi 把这轮拆 prefix（摘要）+suffix（原样保留），用专门的 TURN_PREFIX_SUMMARIZATION_PROMPT 单独摘要前半截。

\- \*\*③怎么压\*\*：prepareCompaction 提取 fileOps（哪些文件被读过/改过，extractFileOperations）→ compact 再调一次 LLM 生成结构化摘要（压缩本身也是 LLM 调用！）→ 新上下文 = 摘要 + fileOps + 保留的近期消息。

\- \*\*④摘要提示词（最值得抄）\*\*：SUMMARIZATION_PROMPT 要求固定格式输出"工作交接文档"——## Goal（用户要什么）/ ## Constraints & Preferences / ## Progress（Done/In Progress/Blocked 三态）/ ## Key Decisions（决定+理由）/ ## Next Steps（有序清单）/ ## Critical Context（精确文件路径/函数名/错误信息）。铁律：保留精确标识符（丢了就接不上）。\*\*UPDATE_SUMMARIZATION_PROMPT 增量更新\*\*：第二次压缩不重新总结全部，而是"上次摘要+新增部分"做 PRESERVE+ADD——压缩本身也省钱。

\- \*\*串回主线\*\*：token 涨过阈值 → AgentSession._handlePostAgentRun（已注释过的函数）调 shouldCompact → prepareCompaction → compact 生成交接文档 → 会话历史变 \[摘要]+\[近期原样]。压缩后缓存前缀全废（日志里 cache r/w 归零的原因），所以 reserveTokens 缓冲带很重要。

\- \*\*范式沉淀\*\*：\*\*压缩 ≠ 总结，是"结构化工作交接"\*\*。固定模板 + 精确标识符保留 + 增量更新，三板斧可直接照抄。



\### ㉕【理解】extensions 扩展系统（收官）



\- \*\*ExtensionRunner 本质：管道式事件总线\*\*。每个 emitXxx 同一模子：for 每个扩展→for 每个 handler→try{ 链式改写（上个输出是下个输入）}catch{ emitError 隔离 }。两个铁律：\*\*责任链模式\*\*（emitContext 里 messages 被逐扩展传递改写——sdk.ts transformContext 钩子的真身）+ \*\*try/catch 隔离\*\*（插件代码不受信任，崩了记 error 带扩展路径/事件名/堆栈，主流程继续）。

\- \*\*钩子三形态\*\*：观察（session 事件只通知）/ 改写链（emitContext、emitBeforeProviderRequest 返回值替换原数据）/ 拦截（session_before 的 result.cancel 一票否决）。

\- \*\*bindCore 反向依赖注入\*\*：构造时私有字段全空实现（\`getModel = () => undefined\`），bindCore 把 AgentSession 真实能力（setModel/compact/getCommands…）拷进 runtime——先有 ExtensionRunner、扩展加载要拿 runtime、但 AgentSession 还没出生的"鸡生蛋"问题，用\*\*可变引用+延迟回填\*\*解决（sdk.ts 的 extensionRunnerRef 空引用技巧完整版）。

\- \*\*能力白名单\*\*：扩展能干什么完全由 bindCore 拷进 runtime 的方法决定——不给的就没有，天然沙箱。

\- \*\*闭环\*\*：扩展文件加载注册 handlers → sdk.ts ⑥ new Agent 时 transformContext→emitContext、onPayload→emitBeforeProviderRequest、onResponse→观察 → runLoop 事件流过 emitMessageEnd/emitToolCall。sdk.ts 见过的所有钩子参数，水源地全在 runner.ts。

\- \*\*可借鉴三件套\*\*：统一 emit 骨架（循环+链式改写+隔离）/ 能力白名单（bindCore 决定扩展权限）/ 诊断不静默（出错进 diagnostics 可溯源）。

提示词工程（魂）   —— 配置驱动生成，工具规约从工具定义生长，技能=提示词分页

extensions（平台） —— 责任链+隔离+能力白名单，core 与插件信任分级

\`\``



\*\*总纲\*\*：harness 的工程密度全在"模型的不可信输出"与"真实世界的副作用"之间的缓冲带上——prepareArguments 纠偏、execute 防御、abort 轮询、责任链隔离，都是这一原则的体现。



\### ㉖【理解】evals 行为评测（2026-08-24 收官）



\- \*\*query\*\*："我在参考下evals咋做的"

\- \*\*核心问题\*\*：改了系统提示词/工具描述后，agent 行为变好了还是变坏了？——用实验代替拍脑袋。

\- \*\*三层架构\*\*：vitest-evals（npm 通用引擎：describeEval/createJudge/createHarness）→ pi-harness.ts（257 行适配层，把 AgentSession 包装成引擎能驱动的 Harness）→ *.eval.ts（用例：smoke 17 行冒烟 / extensions 140 行 A/B 实验）。

\- \*\*pi-harness.ts 隔离设计五步\*\*（一次评测的执行流程）：

  1. \`mkdtemp\` 一次性临时目录（workspace+agentDir）——沙箱里跑，不碰真实文件和全局配置；

  2. \*\*复用装配链\*\*（createAgentSessionServices → createAgentSessionFromServices）+ SettingsManager.inMemory() 设置不落盘 + 启动校验扩展数为 0——评测 = 用 SDK 程序化驱动 agent，IoC 设计的红利；

  3. 多步输入剧本：input 可为 \`\[prompt → reload → prompt]\`——测完整工作流（"让 agent 写扩展→热重载→再用它"），不是单次问答；

  4. setArtifact 留证：runId + 会话快照 jsonl，挂了能回放现场；

  5. finally 必然清理（dispose+rm 临时目录），cleanup 失败走 AggregateError 不静默。

\- \*\*确定性 Judge（不用 LLM 打分）\*\*：ExtensionAuthoringJudge 是纯函数，收集 failures 全过 score=1——检查生成扩展的 import 包名（不许 legacy 包）、扩展加载错误数、\*\*transcript 里有没有一次成功的 hello({name:"Bob"}) 调用且返回正确\*\*、最终回答精确匹配。关键：断言的是 \*\*transcript 行为过程\*\*（toTranscriptEvents 把消息流转成统一事件序列），不只最终文本。

\- \*\*A/B 对比（点睛之笔）\*\*：\`evalHarnessTable({ baseline: 删掉文档段的提示词, candidate: 完整提示词 })\` + \`describe.for\` 同一批用例跑两个变体 → summary.ts（438 行）配对统计：baseline vs candidate 通过率、lift 提升量、token 消耗差、estimatedCostUsd 成本差。直接回答"系统提示词里那段 pi 文档到底有用没"——做实验验证。

\- \*\*借鉴清单\*\*：①eval 三件套=沙箱隔离+确定性 judge+artifact 留证；②断言 transcript 而非最终文本；③A/B 思维：每次改提示词/工具描述都跑 baseline vs candidate；④剧本式输入测工作流；⑤成本也是指标（token/耗时/美元进报告，行为变好但贵三倍可能是坏事）。

\- \*\*定位认知\*\*：evals 是"慢而贵"的测试（真实调 LLM），与单元测试分离（test.sh 的 "skips LLM-dependent tests without API keys" 就是这层）。

\## 五、设计范式 Checklist（做自己的 agent 时对照用）



\> 从 26 条记录中提炼的可落地范式。动手做项目时逐条对照，不必重读全文。



\| 范式 | 出处 | 我做 agent 时怎么用 |

\|---|---|---|

\| 模型输出不可信，校验前先有纠偏层 | ㉒ edit.ts prepareArguments | 每个工具写 prepareArguments，收集各模型的坏毛病（JSON字符串化/单对象不包数组） |

\| 压缩≠总结，是结构化工作交接 | ㉔ compaction | 抄 Goal/Progress/Decisions/NextSteps/CriticalContext 模板 + 精确标识符保留 + 增量更新 |

\| 技能=提示词分页，菜单+read 自取 | ㉓ skills.ts | 系统提示词只放技能目录（name+desc+路径），正文让 agent 用 read 工具按需加载 |

\| 工具规约三重冗余 | ㉒ edit.ts / ㉓ system-prompt | 同一规则写三处：schema description + 工具 description + 系统提示词 guidelines |

\| 打断要体面：try/catch/finally 三段式 | ⑲ activeRun | abort 后包装成正常消息收尾（stopReason=aborted 非 error），finally 复位状态 |

\| 互斥+插队，而非并发 | ⑪⑲ Agent | 一次只跑一个 loop；运行中输入走 steering 队列在当前 turn 后插入 |

\| 统一中间格式，厂商差异关适配器 | ⑳ 六边形架构 | 先定 Context/Event 词汇表，再每家写双向翻译器，厂商 SDK 类型不进循环 |

\| core 与插件信任分级 | ㉕ extensions | 责任链 emit 骨架（循环+链式改写+try/catch 隔离）+ bindCore 能力白名单 |

\| 配置驱动的提示词生成 | ㉓ system-prompt | 提示词按当前工具集条件生成，不给不存在的工具的指引；customPrompt 与核心上下文解耦 |

\| 评测：确定性断言 + A/B 对比 | ㉖ evals | 把任务设计成可断言的（transcript 断言 > 文本断言）；改提示词必跑 baseline vs candidate |

\| 工具的防御性执行 | ㉒ execute 四层防御 | 文件锁串行化 + abort 轮询（非事件）+ 编码归一化 + 错误回喂模型自我修正 |

\| IoC 装配：core 纯逻辑，启动时注入 | ⑯⑳ sdk.ts/stream-fn | core 不 import provider，留注册点由 host 启动时注入；先有鸡先有蛋用可变 ref 回填 |

\## 六、数据词汇表（pi 统一中间格式·标准字段全览）



\> 来源：\`packages/ai/src/types.ts\`（标准定义）+ pi-traffic.log（实物验证）。

\> 这是六边形架构的"地基"——10 个 api 适配器的入向/出向翻译都以这套格式为准。

\> 自己做 agent 项目时，这份词汇表可以直接当中间格式参考。



\### 1. 发给 LLM 的请求体：\`Context\`



\`\``typescript

interface Context {

  systemPrompt?: string;   // buildSystemPrompt 的产出（㉓ 五层组装）

  messages: Message\[];     // 完整对话历史（三种 role，见下）

  tools?: Tool\[];          // 工具说明书清单（createCodingTools 的产出）

}

\`\``



实物（pi-traffic.log 首条记录）：\`{ type:"request", tools:\[…4个], messages:\[…], systemPrompt:"You are an expert coding assistant…" }\`



\*\*Tool 说明书\*\*（给模型看的半边契约）：



\`\``typescript

interface Tool {

  name: string;         // "read" | "bash" | "edit" | "write" | …

  description: string;  // 自然语言使用说明（含规约，㉒ 三重冗余之一）

  parameters: TSchema;  // typebox JSON Schema（如 editSchema：path + edits\[]）

}

\`\``



\### 2. 对话历史：三种消息角色



\`\``typescript

type Message = UserMessage | AssistantMessage | ToolResultMessage;



interface UserMessage {

  role: "user";

  content: string | (TextContent | ImageContent)\[];  // 文本或文本+图片

  timestamp: number;

}



interface AssistantMessage {   // 模型的一轮输出（done 事件的 message 实物字段全对得上）

  role: "assistant";

  content: (TextContent | ThinkingContent | ToolCall)\[];  // 三种内容块混合

  api: Api;                  // "openai-completions" 等（协议，非厂商！）

  provider: ProviderId;      // "deepseek" 等

  model: string;

  responseModel?: string;    // 路由后实际模型（OpenRouter auto → 具体模型）

  responseId?: string;       // 厂商侧响应 ID

  usage: Usage;              // token 与成本（见下）

  stopReason: StopReason;    // 本轮为何结束（见下）

  rawStopReason?: string;    // 厂商原始 stop 值（调试留证）

  errorMessage?: string;     // stopReason=error/aborted 时的原因

  timestamp: number;

}



interface ToolResultMessage {   // harness 执行完工具后回喂的消息

  role: "toolResult";

  toolCallId: string;        // 对应哪个调用（与 ToolCall.id 配对）

  toolName: string;

  content: (TextContent | ImageContent)\[];  // 工具产出（支持图片！read 读图靠它）

  details?: any;             // harness 自用附加信息（如 edit 的 diff/patch）

  isError: boolean;          // 工具失败也回喂（模型下一轮自我修正，㉒ 防御第4层）

  timestamp: number;

}

\`\``



\*\*内容块（content 数组的元素）\*\*：



\| 类型 | 关键字段 | 说明 |

\|---|---|---|

\| \`TextContent\` | \`text\` | 普通文本 |

\| \`ThinkingContent\` | \`thinking\` / \`thinkingSignature\` / \`redacted\` | 思考过程；signature 是厂商回放思考链的不透明凭证 |

\| \`ImageContent\` | \`data\`(base64) / \`mimeType\` | 图片 |

\| \`ToolCall\` | \`id\` / \`name\` / \`arguments\` | \*\*模型"说"出的调用请求\*\*（㉑ tool 本质的实物） |



\### 3. 流事件：\`AssistantMessageEvent\`（11 种全览）



\> 模型响应不是一次返回，是逐字流出的事件序列。三种内容通道（文本/思考/工具调用）各有 start→delta→end 三拍。



\| 事件 | 额外字段 | 含义 |

\|---|---|---|

\| \`start\` | \`partial\` | 流开始，partial 是逐步累积的半成品消息 |

\| \`text_start\` | \`contentIndex\` | 开始一个文本块 |

\| \`text_delta\` | \`contentIndex\`, \`delta\` | \*\*逐字流出正文\*\*（delta=本次新增字符） |

\| \`text_end\` | \`contentIndex\`, \`content\` | 文本块完成（content=完整文本） |

\| \`thinking_start/delta/end\` | 同上 | 思考通道（thinking_delta 可拼出决策心路） |

\| \`toolcall_start\` | \`contentIndex\` | \*\*模型开始"说"工具调用\*\* |

\| \`toolcall_delta\` | \`contentIndex\`, \`delta\` | 调用参数 JSON 逐字流出（㉑ 实验里看到的那串） |

\| \`toolcall_end\` | \`contentIndex\`, \`toolCall\` | 参数输出完毕，toolCall=解析好的完整调用 |

\| \`done\` | \`reason\`, \`message\` | 成功结束，message=最终完整 AssistantMessage |

\| \`error\` | \`reason\`, \`error\` | 失败结束（aborted/error），error 也是 AssistantMessage 形态 |



\*\*协议约束\*\*：\`start\` 必在最前；结尾二选一——\`done\`（成功）或 \`error\`（stopReason 为 error/aborted 并带 errorMessage）。



\### 4. 结束原因：\`StopReason\`（7 种）



\| 值 | 含义 | 工程动作 |

\|---|---|---|

\| \`stop\` | 正常说完 | 无 |

\| \`toolUse\` | 要调工具 | runLoop 内层 while 再转一圈 |

\| \`length\` | 输出超 token 上限被截断 | \*\*截断保护\*\*：tool call 可能残缺，拒绝执行（agent-loop.ts 注释） |

\| \`error\` | 出错 | errorMessage 回显 |

\| \`aborted\` | 用户打断 | ⑲ 体面收尾，不报错 |

\| \`pending\` | 流进行中（中间态） | — |

\| \`deferred\` | 厂商挂起（如批量任务），稍后轮询 | 少见 |



\### 5. 用量：\`Usage\`（状态栏数字的产地）



\`\``typescript

interface Usage {

  input: number;        // 输入 token（状态栏 "in 2,709"）

  output: number;       // 输出 token（"out 46"，含 reasoning）

  cacheRead: number;    // 命中缓存的输入（"cache r/w" 的 r，省钱关键）

  cacheWrite: number;   // 写入缓存（w）

  reasoning?: number;   // 思考 token（output 的子集，非所有厂商上报）

  totalTokens: number;

  cost: { input, output, cacheRead, cacheWrite, total };  // 美元成本（evals ㉖ 的指标来源）

}

\`\``



\### 实物样本（pi-traffic.log 已验证字段）



\- \`done.message\` 实物字段：\`role/content/api/provider/model/usage/stopReason/timestamp/responseId/rawStopReason\`——与标准定义一致

\- 一次真实事件序列：\`start → thinking_start → thinking_delta×19 → toolcall_start → toolcall_delta×11 → thinking_end → toolcall_end → done(toolUse)\` →（harness 执行工具、回喂 ToolResultMessage）→ \`start → text_start → text_delta×35 → text_end → done(stop)\`

\## 七、自主学习思路大纲（收官总结）



\> 回顾 26 条学习记录提炼的完整路径——这条路径本身可复用于下一个开源项目。



\### 第一阶段：建立全局认知（不动代码，先画地图）



1. \*\*scripts 是仓库的地图\*\*：37 条命令 = "这个仓库能干什么"；build 的 cd 顺序 = 依赖序的可执行版本（①）

2. \*\*区分启动器与入口\*\*：pi-test.sh 是启动器不是入口；\`export ≠ execute\`，找顶层调 main 并处理 argv 的地方（②⑥）

3. \*\*packages 目录分层\*\*：按依赖方向画出 L0 地基→L1 模型→L2 内核→L3 产品→L4 质量（四）



\### 第二阶段：自顶向下追主线（从入口到核心循环）



4. \*\*main.ts 主干六步\*\*：重要性分级——主线细读、分支扫一眼、平台适配跳过（⑦）

5. \*\*选用户视角的终点深入\*\*：InteractiveMode 入手，用到装备时再回头看装配（⑧）

6. \*\*挂起-唤醒模型\*\*：\`while(true){await}\` ≠ 轮询；getUserInput 是 Promise 挂起（⑩）

7. \*\*状态在哪重置\*\*：finally 里——两层互斥锁（_isAgentRunActive / finishRun）（⑪）

8. \*\*IoC 容器思维\*\*：runtime 持有 session+services+工厂，/resume = 拆旧→再造→换芯（⑬）

9. \*\*装配链七阶段\*\*：createAgentSession 把零件组装成机器；先有鸡先有蛋用可变 ref 回填（⑯）



\### 第三阶段：吃透内核（agent-core）



10. \*\*有状态外壳+无状态循环\*\*：Agent 类管状态与事件，runLoop 是纯函数——可测试性的来源

11. \*\*activeRun 三重职责\*\*：互斥锁+abort 靶子+等待句柄；打断是体面收尾不是崩溃（⑲）

12. \*\*串行+插队模型\*\*：一次一个 prompt 跑到底，运行中输入走 steering 队列（⑪）

13. \*\*streamFunction 依赖反转\*\*：core 不 import provider，启动时注入（⑳）



\### 第四阶段：协议适配层（ai 包）



14. \*\*按协议分不按厂商分\*\*：10 个 api 适配器对应 10 种方言；注册表键是 model.api（⑳）

15. \*\*适配器同构三件事\*\*：出向翻译→SSE 流→入向翻译；统一词汇表是地基（⑳、六）

16. \*\*六边形架构落地\*\*：core 只定义中间格式，厂商差异全关在适配器（⑳）



\### 第五阶段：Harness 四大件（工程密度最高处）



17. \*\*tools（手）\*\*：契约=说明书+执行体；prepareArguments 纠偏层写厚；execute 四层防御（㉑㉒）

18. \*\*提示词工程（魂）\*\*：配置驱动生成；工具规约三重冗余；技能=提示词分页（㉓）

19. \*\*compaction（记忆）\*\*：压缩≠总结，是结构化工作交接；固定模板+精确标识符+增量更新（㉔）

20. \*\*extensions（平台）\*\*：责任链+隔离+能力白名单；core 与插件信任分级（㉕）

21. \*\*evals（质量）\*\*：沙箱隔离+确定性 judge+A/B 对比；断言 transcript 而非文本（㉖）

22. \*\*审批哲学\*\*：core 只给机制（beforeToolCall 钩子）不给策略，策略留给扩展（bash 篇）
